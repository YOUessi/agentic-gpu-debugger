# 历史回补 02：批量入口、可信证据、授权与恢复

回补日期：2026-09-29。证据来自 Git、`docs/GPU_BATCH_CURRENT_CN.md`、模式契约、
执行/隔离设计文档以及当时用户转述的外部补丁说明。不同来源的可信程度分别标明。
这篇记录历史工程边界，不重新要求用户指定评审人或以正式发布程序阻塞项目修改。

## 第一轮：压缩包交付不能直接视为本地合并和验收

### 问题和原因

外部交付包含源码、补丁、测试记录和运行说明，但用户曾反复追问测试使用的是
压缩包还是本地工作区、是否解压、结果在哪。这说明当时回答没有清楚绑定实际 checkout。
交付方报告 35/180 或 61/333 等测试数字，还明确没有真实 GPU 验证、云端依赖不全。
这些数字不能自动成为本机代码的测试结果。

### 应该如何处理

记录包名、解压位置、基线提交、应用检查和实际执行目录；把“外部声称通过”与
“本机执行通过”分开。补丁应用成功也不等于行为正确，必须核对差异及受影响测试。

### 实际可确认的修改与结果

本轮核对到 `0d84d2d` 正式加入 batch、batch_models、batch_report、batch_security、
`gpu_batch.sh` 和对应测试，接通 run-seeds / batch-report / export-batch。
但本轮未重新解压全部早期 ZIP，也没有恢复每次试用的临时目录，因此不编造
“每个压缩包测试了几项”的本地结论。旧外部数量仅保留为转述，未再执行交付脚本。

## 第二轮：批量入口必须复用可信 family，不能顺手新建授权体系

### 问题与为什么出现

外部批量入口早期设计涉及隐式创建 family/ledger、只按路径检查锁、导出全部直接
子节点和信任缓存摘要。这会使“方便运行”跨越原有授权/证据边界：同路径对象可能
被替换，非本批运行可能混入导出，缓存字段可能与原始日志不一致。

### 应该如何修复

真实运行应使用已有可信 family；静态预检查不创建新 authority。锁和目录需要
所有权、权限、类型、硬链接及 fd/device/inode 身份检查。导出应由本批明确记录的
run ID 白名单驱动，核对 case、role、parent、binding 和可见性，再核验每项哈希。

### 实际实现和可验证结果

`0d84d2d` 的实现及现有运行说明体现这些限制：parent 为绑定一致的 RUNNING seed_batch，
summary 指定 clean/mutant，原始日志重新派生结果；注册仍交由原有 Builder/ledger，
默认只验证，显式请求才注册。ZIP 输出不覆盖已有文件，不打包控制器密钥、ledger 或
evaluator 私有资料。新增测试文件提供边界复现，但本轮未找到该次完整本机测试 stdout，
不把交付方 333 passed 写成本地验收。

## 第三轮：预期 Sanitizer 类别与原生输出不一致

### 问题、原因和方案

case_0001 注册表原先预期 `Invalid __global__ write`，后来记录到的是 read；
case_0002 原先预期 Write/Write，原生报告是 Write/Read。故障存在，但注册验证的
精确类别对不上。修复不能是看到失败就随意换标签，而应核对实际源码操作和原始工具输出。

### 实际修改与测试证据

`2b683b9` 同步修订 case_0001 注册表与 GPU 测试预期；`10d7901` 修订 case_0002，
并加入 `test_case_0002_registry_matches_observed_write_read_race`，使用记录格式的
Sanitizer 文本验证解析结果与注册预期一致。这两个 diff 本次已核对。
第二个提交中的日志 fixture 是测试输入，不能当作本轮重新运行的 GPU 输出。
当时逐次 GPU 命令/通过总数未在这里恢复，保留证据缺口。

## 第四轮：自报“通过”不足以证明执行证据来源

### 问题与设计缺口

早期曾实现不可变评测/发布声明，但 `fd7bf60` 明确回退 unproven release attestations。
该提交删除大量 release 逻辑和测试，并修改验收说明。这可确认当时撤回过缺少充分
原生证据支持的声明；不能仅凭“有签名/有 hash”证明数据来自正确的 GPU/模型流程。

### 应该与实际如何修复

后续 `f266811`、`b30b91a`、`83a2e64` 建立执行前绑定与跨执行域 provenance；
`3b2d5b8`、`263166f`、`c7b6dd5`、`568dcc8` 对原生 corpus 注册和崩溃恢复加固。
这些提交在历史目录中可定位。它们的共同方向是从真正的运行、产物和状态转换
推导可信结论，而非信任外部给出的成功字段。本轮未逐一重演崩溃点，不给每个提交
补造测试结果；完整提交标题清单见历史索引附录。

## 第五轮：授权、cutoff、锁与恢复是跨模块状态问题

### 问题和原因

Git 中存在连续的 schedule authority、reservation、lease、cutoff、inode pinning
修复。若校验和执行不在同一稳定身份/状态上，就有机会出现校验的是一个对象，
使用的是另一个对象；恢复若重新创建已执行单元，又可能重复调用模型或混用语料快照。
这是这组修复所针对的边界风险，不代表本轮证明所有风险都曾被实际利用。

### 应该如何修复与实际变化

相关历史从 `8eee211` 外部签名授权，经 `0b80726`、`500cb18` 等冻结/pin 运行状态，
到 `cef6529`、`e202b5a` 等约束 cutoff 的预留和提交顺序。holdout 相关提交将执行
产物放入 evaluator store，公开端保留承诺而非私有源码；验证读入受绑定控制。
重复审查造成了很多小提交，但不能把提交数量解释为已完成了同等数量的独立任务。

### 结果、限制和后续

本篇只核查提交序列与设计/模式契约，没有打开 evaluator 数据。可确认后来的
`9d75699` 实现规定已开始但缺少完整 completion receipt 的单元保持不确定，
resume 不重新派发诊断/验证；只有原生证据与调度复算一致时恢复公开记录。
正常流程检查新记录，恢复和最终审计保留完整核验。

早期每轮锁竞争、崩溃恢复及私有可见性测试的完整结果尚不能从当前资料逐个恢复，
因此状态是“源码/测试/设计可追溯，逐次运行证据未补齐”，不是笼统“全部通过”。
后续收尾中发现的真实失败、完整批次结果以及输入预检修订见第 06 篇。
