# 历史回补 05：同步补丁错误、静态检查误判与有界反例

回补日期：2026-09-29。主要证据是 `docs/sync-participation-review-CN.md`、
0a56f08/cdd629f/31679d1 的历史，以及仍保留的公开同步审计目录。本文不是重新读取

## 第一轮：有诊断和补丁，但补丁扩大了错误调用者集合

### 问题和原因

公开 case_0015/E 的模型候选把同步调用前的条件移除，使更多线程执行调用，但 mask
并没有相应包含这些线程。GPU synccheck 仍报告原问题。它首先是候选程序逻辑错误，
不是 HTTP API 出错，也不是验证器“故意不通过”。

### 应该如何修复

不能由开发者把正确 case 阈值写进模型输出，不能放宽 GPU 标准。可考虑对所有模式
一样的源码约束检查：只根据候选文本推导可证明的违规，并把不确定情况明确留给运行验证。
该检查是在看过公开开发失败后设计的，属于下一版本变更，评测必须分开保存。

### 实际变化与证据

外部 sync-participation 补丁试图检查所有参与一致性；本机审查没有直接启用其全部
拒绝规则。后续实现限制在可分析子集：只拒绝确实调用同步、但自身 lane 位不在 mask
中的线程；不能计算的控制流、类型和动态行为保持 UNANALYZABLE。所有 A–E 模式一致，
不读 case 标签或正确答案，不产生参考补丁。

## 第二轮：原静态方案与运行时 CLEAN 有九项分歧

### 问题、原因与区分

历史审计共 88 条候选对照，29 条 synccheck CLEAN 中有 9 条被旧算法标记。
不能假定静态检查一定正确，也不能看到 CLEAN 就自动证明源码满足全部规则。

其中 8 条属于“具名线程在该源码点没有调用”。简化分析器无法证明动态执行中的
退出/到达关系，因此其推理前提不足。另一条为调用线程自身缺位，需要进一步检查
实际生成代码，不能混为同一种误报。

### 应该与实际怎么修复

将无法证明的到达/退出情况改为未知，而不是宣布源码正确。修正短路运算/条件表达式
的条件执行、ballot 的分组 mask、八进制字面量、巨大位移和不可靠类型推断；遇到
未知函数、宏控制、动态 launch、重名函数等不作确定结论。31 种 mask 宽度和多 warp
正反例用于避免只适配一个 case。

剩余候选 `926f143ca1cfce72ded9688ef64edb36` 的历史隔离编译中，PTX 仍含
`bar.warp.sync 65535`，但 SASS 对应 kernel 无 warp 同步指令。于是源码违规与运行时
CLEAN 可以同时成立；静态告警不能冒充 Sanitizer finding。
