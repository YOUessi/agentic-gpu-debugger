## case_0022 的实际补丁与失败归因

V2 首候选把循环中的屏障移动到写之后并增加初始化屏障，普通数值输出通过但 `racecheck=FINDING` 且 `synccheck_functional=NUMERIC_MISMATCH`。第二候选保留循环原有的写前屏障，同时在写后增加屏障，并保留初始化屏障；独立验证 `VERIFIED_FIXED`。

V3 第一候选把屏障移到写后，普通数值发生 `NUMERIC_MISMATCH`；触发 `REINVESTIGATE`。第二候选加入初始化屏障和写后屏障，普通数值通过，但 Racecheck 仍报告竞争，Synccheck 下数值不匹配。此时重新调查次数已经用完，进入普通修订。第三候选在循环后另加屏障，但又出现数值不匹配。最后 `stop_reason=CANDIDATE_LIMIT`，未执行独立验证。

**真实机制问题**：重新调查和反馈虽然正常执行，模型并没有稳定地保持同一个共享内存迭代中的“读后写前”及“写后进入下一次读前”的同步约束。这是下一版诊断与修订策略最有价值的候选优化点；不应简单归因于 DeepSeek API 故障，也不应用额外抽样抹去该失败。

## 证据与风险边界

原始公开 RunStore 位于 Tang 的 `/home/you/gpu-agent-repair-v3-compare-20261009-01/unit-00` 至 `unit-03`，预声明调度和结果文件位于上一层目录。模型调用数量、Token、候选结果与公开失败反馈由 `result.json` 和 RunStore 可查。GitHub 附件是从这些结果核对后整理的公开摘要，**不是原始 CLI 输出**。结果文档未复制模型凭据、私有测试输入、未授权隐藏期望值或完整外部请求响应 ID。

本轮真实结果不证明 V3 优于 V2，也不能以单次 V3 失败声称其整体弱于 V2。要判断效果，需要预先固定更多案例、重复次数、相同预算和模型设置，将“有无重新调查”与“有无 Sanitizer 单独上限”拆开为独立因子。与此同时，工程层面已经证实 V3 的重新调查确实能启动，但复杂同步问题上的修复策略仍不稳定。
