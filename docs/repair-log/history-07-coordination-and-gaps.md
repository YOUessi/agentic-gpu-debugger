# 历史回补 07：版本沟通、任务范围与尚不能完整恢复的记录

回补日期：2026-09-29。此篇依据当前对话中保留的用户反馈、仓库实际文档和可核对
提交。没有完整原回复的场合，不编写虚构引语，也不把用户质疑自动当成已证实的代码缺陷。

## 第一轮：分支名字被当作任务进度，用户无法知道做到哪里

### 问题与原因

对话里多次出现“怎么又回到 task1”“task4/5 不是做完了吗”“到底做到哪里”。
分支长期叫 feat/t01-environment 不代表只做了 T01；一轮修复通过也不代表 T01–T12
或 V2 所有要求都通过。若状态回答不引用具体代码、证据和未完成项，就会反复混淆。

### 应该如何修复与已有实际处理

应按功能/验收项列已实现、已验证、尚未验证，不拿分支名和提交数替代进度。
仓库后来增加 v2-release-status、evaluation-report、acceptance 和 closeout 文档。
本轮又将问题按主题和轮次记录，每次说明证据级别，不自动相信旧状态页的“current”。
例如旧状态页仍描述 79 个片段/17–29 的旧检索，这是历史状态；当前新结果应引用
20260929 文档，不能把两者同时当成现状。

### 验证结果与边界

可以核对文件与提交的存在，但无法用代码测试证明过去每一次状态回复都准确。
本次的改善是有可追溯索引和新规则，后续仍须实际遵守，不能宣称“沟通错误永不再发生”。

## 第二轮：没有区分模型 API 密钥、Git 凭据和控制器密钥

### 已知问题与不能补造的部分

用户曾多次说明自己不知道该填哪个 key、项目中已经填写过 DeepSeek API。
对话表明当时解释没有充分区分 Git 登录/SSH、模型 API 和控制器授权资料。
本篇不记录任何密钥值，也不把未核实的历史文件路径列成当前配置事实。

### 应该如何处理与实际可核实状态

应先说明是哪种凭据、服务用途、现有配置路径，再判断是否缺失，不能要求用户
凭空提供不存在的东西，也不能因为没在当前 shell 看见变量就断言项目没有 key。
检索修复时已实际核对 provider.env 的知识库配置并仅改索引行，未打印/改动 API key。
这证明最近一轮使用了明确的配置位置，不足以还原早期所有凭据操作的命令和时间。

## 第三轮：持续回归和费用边界没有遵循用户的操作偏好

### 问题与原因

用户明确要求只复测失败项、不要反复跑正确项、不设置美元硬上限、不查询余额，
还多次指出频繁轮询和长期离线回归看不到实际实验进展。若控制器或运行计划仍按
旧的 cost-bounded 思路执行，就与当时授权不一致。

### 应该与实际如何修复

9d75699 的模式契约明确改为 record-only：不因金额拒绝运行，usage/费用未知保留
null，兼容读取旧字段不等于继续用其控制执行。请求次数/任务期限与美元上限分别说明，
不把前者偷换成后者。后续八项复测只选原两项格式和六项超时，维护轮仅回归受影响模块。

### 结果与后续约束

这些有提交、selection/completed 和文档支持，但不能证明历史每次调用都符合偏好。
今后先记录测试选择及理由；不会因“记录要完整”而重新跑已成功实验。新文档规范
明确要求不新增金额上限或余额检查，不把用户要求完美等同无限重试模型。

## 第四轮：把正式评分/发布程序当成用户必须完成的新需求

### 问题与范围偏移

用户反复强调目标是完善一个用于 NVIDIA 求职的项目，不理解为何突然要求指定独立
评审人或让其他人安装。仓库规格确实存在 formal release/盲评要求，但文档中的
研究验收设计不能自动变成阻止代码修复或向用户添加新义务的理由。

### 应该如何处理及此次实际修正

应该解释“代码可用/工程缺陷”“模型表现”“正式评分”各自是什么，按用户当下要求
工作。可以如实说独立评分尚无证据，不得因此伪造评分，也不能反复要求用户去找人。
此次回补保留 historical gate 未通过的事实，同时明确本轮不恢复该流程、不增加
评审/部署任务，不用那些条件宣布整个求职项目无效。

### 验证边界

这是范围管理与汇报纠正，不是修改业务逻辑，不能以 pytest 数量证明它已永远解决。
后续交接必须说明当前用户请求是否完成，不能拿另一套发布流程替换用户目标。

## 第五轮：把模型没修对与 Agent 实现缺陷混成一种“问题”

### 问题与原因

用户多次问为什么 case_0010 写冲突仍在、为什么出现无法判断，是否都是 DeepSeek
问题。旧回答如果只报 FAILED 或只说继续修，会让用户无法区分 API 故障、模型选择、
候选逻辑错误、工具拒绝和项目代码缺陷。

### 应该与实际如何改进记录

应按发生阶段和证据分类：无法判断是模型输出的一种结果；错误补丁要看公开候选与
GPU 发现；格式失败看 JSON/schema/策略码；超时根因没有证据时保持未知；缓存和
版本加载错误则属于可复现的项目实现/配置问题。第 03–06 篇逐项采用这个区分。
不能因模型原因完全免除 Agent 的接口/观测责任，也不能为模型每次不答对无限改代码。
