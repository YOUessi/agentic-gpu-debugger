# 历史回补 03：评测语义、按案例验证、执行版本与性能缓存

回补日期：2026-09-29。主要证据为 `9d75699` 的实现/模式契约、`87fa492`、
`docs/maintenance-20260928-CN.md` 和本机保留的离线日志。早期 240 单元统计中部分
只有用户转述的 Claude 分析，本篇明确区分转述与重新核实。

## 第一轮：早期五模式没有实际测量规格中的变量

### 问题与为什么出现

早期审阅指出 A–D 使用控制器确定性诊断而不调用同一个 LLM；A/B 没工具发现就
得不到诊断，D 抄取 Sanitizer 类别导致高分，C 有工具证据却被文档条件拒绝。
这种行为把“证据获取策略差异”和“诊断器本身差异”混在一起，无法回答 Agent
是否优于规则获取策略。批次 COMPLETED 只代表单元处理完，不代表比较设计成立。

转述的 c7172c8 批次为 240 单元，A/B 各 48 FAILED，C/D 各 48 INCONCLUSIVE，
E 48 FAILED；E 的 123 次调用全部为 planner。上述数字本次未逐条重新聚合，因此
保留为外部分析记录，不包装成本轮已核实原始账本。

### 应该怎么修复

所有模式共用诊断、补丁 provider 和验证器，只改变允许获得哪些证据/如何获得。
证据要求必须与本次确实获得的证据一致，不能要求 A 提交其契约禁止获取的发现。
诊断成功、补丁生成、验证修好要分别统计，不用 COMPLETED 代替修复成功。

### 实际如何修复

本次核对 `9d75699:docs/mode-contract.md` 和相关变更：删除确定性诊断与
controller-only provider 路径；A 是普通执行，B 增加检索，C 固定工具获取，
D 为 RuleRouter，E 为 Planner，但诊断/补丁/schema/验证共用。引用检查由真实
获得的证据派生，并保存模型诊断与最终派生诊断供复算。

增加冻结的 failure_family 词表和公开开发标签，而不是用原始工具报错文本随意计分。
根因和位置未有有效裁定的部分不伪装成独立人工分数。实现与测试源码可确认；本轮
未补造 9d75699 全量离线通过数。后来的真实结果见第 06 篇，不回写早期批次。

## 第二轮：验证器不能只认一个案例，也不能只看 memcheck

### 问题和原因

初版 truth/hash 只绑定 case_0001，缺陷是否仍在主要看 memcheck。其他 case 的
原始源码无法匹配该基线，而 race/sync 缺陷即便数值输出正确仍可能存在。
若验证还依赖 Agent 是否先运行 Sanitizer，A/B 就在结构上无法得到公平验证。

### 应该与实际如何修复

`9d75699` 新增 `verification/truth.py`：公开案例根据原始 kernel hash 唯一匹配
registry，使用该 case 的 target_tool 和 expected_finding，并核对 harness。
共享 vector-add oracle 参数仍可来自一个基础 truth 文件，但不再把所有 mutant
限制为 case_0001 的源码。未知或不支持的 oracle 保持无法判断，不猜出一个答案。

每个验证输入运行 memcheck 和案例目标工具；full 模式按契约再覆盖其他工具。
验证依据不依赖 Agent 之前是否收集过该工具的证据。私有 truth 解析限定 evaluator
注册证据、cutoff 和身份，不能把私有描述反馈给模型。本轮只读取实现/契约，未读私有内容。

### 测试与边界

对应提交增加 `test_private_verification_truth.py`，改写 verification_engine 与
mode_contract 测试。存在测试文件不等于当时运行全部通过，历史输出未在此恢复。
后续 case_0015 的 full 四工具通过和冻结批次是具体运行证据，见相应历史篇。

## 第三轮：固定输入和源码提示泄漏破坏评测有效性

### 问题与方案

所有 case 一律用 n=257，可能与注册时确认缺陷的输入不同；源码里的 Intentional
benchmark defect 注释及提示性函数名会向模型泄露故障意图。前者让诊断和注册
不是同一个实验，后者让模型得到不应有的答案提示。

### 实际修改与验证边界

`9d75699` 为 16 个公开案例保存 `public_input/input.json`，执行/回放核对输入 hash；
去除缺陷注释和提示性命名，case_0001 不再把输入长度写死为 257。旧的 case_0002–0004
冗余 development truth 文件删除，打包清单同步变更。源码哈希变化意味着旧注册
不能自动给新源码背书，必须使用新的合法验证/注册记录。

这一轮是防泄漏与输入一致性修复，不是让模型能力变强；不能把新成绩归因于单一改动。

## 第四轮：执行代码不等于操作界面显示的仓库版本

### 问题、原因和实际修复

外部审阅曾基于 e19b9e5 推断 c7172c8 的行为，又发现旧实验通过 recovery 文件
应用运行时补丁。这里要分开两件事：审阅版本不一致导致结论可能错误；混合代码状态
的结果也不能冒充同一干净提交的评测。早期 recovery 时间线本次没有逐项重放。

`9d75699` 增加 runtime_code_hash，for_release 要求实际导入的 gpu_agent 位于
捕获仓库的 src 下，每个单元核对执行代码，漂移时停止。运行 claim 与 completion
也进入精确产物清单。已核对 release.py 差异，因此“9d75699 必然不含 claim 修复”
是不能继续使用的旧推断。2026-09-29 又确认日常 editable 环境仍加载旧发布目录，
属于配置接通问题，详见检索逐轮记录第六轮，不应与此历史结论混淆。

## 第五轮：减少重复历史扫描，但不虚称整个批次已证明 O(n)

### 问题与原因

早期外部报告单元之间间隔随数量增长，推测每个单元反复扫描/解析全历史导致平方级
退化。9.5 小时、95% 等数字来自转述，本次未重新计算，不作为本轮性能实测。
仅证明 validator 调用次数受控，也不能证明 listdir 次数、解析字节或总墙钟线性。

### 应该与实际如何修复

9d75699 对正常路径只验证新记录，增加 store inventory/manifest 缓存，对目录扫描、
validator 次数、manifest 解析字节和规模增长做测试；恢复/终审仍全量核验。
文件身份、mtime、ctime、大小参与失效判断，目录事件队列丢失时重扫，fork 后独立监听。
但子目录 stat 和逐渐增长的父 manifest 写入仍存在，模式契约明确不声称总流程严格 O(n)。

### 第一阶段结果与新问题

后续完整离线回归在日志中实际出现 1350 passed、1 failed、47 deselected，1230.09 秒。
唯一失败是 `test_cached_manifest_detects_replacement_and_same_size_edit`：
期望改写后 `other`，实际仍返回 `first`。这证明优化引入/暴露了真实缓存正确性缺口，
不能因其余测试通过就宣称缓存可靠。

## 第六轮：同长度改写并恢复 mtime，stat 缓存仍会漏失效

### 已确认原因与修复方案

文件同长度快速原地改写，恢复 mtime 后，文件系统 ctime 也可能仍相同。
只靠 stat 元组不能可靠感知写入。应补写入事件代次，并在监听缺失或队列溢出时
保守重新读取，而不是恢复成每个单元解析全部历史 manifest。

### 实际修复和测试结果

`87fa492` 增加 `file_changes.py` 并修改 store 缓存：写事件改变代次，事件丢失使
缓存失效，监视不可用时重读，fork 子进程有独立队列。新增队列溢出、不可用、fork
和同长度改写测试。修订后受影响模块 137 passed，日志实际保留 8.19 秒；文档另记录
连续 1000 次同长度改写/恢复 mtime 均正确失效。Ruff 与 strict mypy 通过。

`gpu-agent-offline-20260928.log`、对应 XML、`changed-modules.log` 和 XML。
本次只读核对了日志末尾失败/通过信息，没有重跑测试。完整原命令的所有参数未从
