# 项目逐轮问题、修复与测试记录规范

## 一、用户要求与适用范围

从 2026-09-29 起，每一轮问题都必须详细记录以下内容：出现了什么问题、为什么
出现、应该如何修复、实际如何修复、测试结果是什么；如果仍未达到本次任务的
验收标准，就继续下一轮，并把下一轮同样完整写下来。

这项要求适用于本项目后续的代码、配置、知识库、Agent 行为、GPU/API 实验和
测试问题。记录必须是可独立阅读的中文文字说明，不能只有聊天摘要、提交标题、
命令列表、截图或“已修复 / 测试通过”。代码和原始日志是证据附件，不能代替解释。

## 二、记录组织与更新时机

每个问题主题建立一个 `YYYY-MM-DD-主题.md`，在同一文件中按第一轮、第二轮
顺序追加。新问题主题再建立新文件，并在本文件的索引中增加链接。
采用 [记录模板](TEMPLATE.md)，不适用的部分要说明原因，不应悄悄删掉。

开始排查时先写背景、已知现象、验收标准和证据位置；确认原因时补证据和推理；
修改后补实际改动；命令结束后立即补测试结果。交接前核对文档与真实工具输出。
不要等到所有事情结束后只补一个成功总结。若本轮被中断，写清实际停在何处、
哪些进程仍在运行及恢复所需信息，不能写成完成。

历史记录只能追加纠正或清楚标明更正，不能抹掉失败。回补旧记录时必须说明它是
回补，哪些来自现有文件，哪些来自对话工具输出，哪些原始日志没有保存。

## 三、每轮必须回答的问题

1. **问题是什么。** 写触发条件、实际表现、预期表现、影响范围和具体失败项。
   “检索不好”“测试挂了”不够，要说明哪条输入、哪个阶段、什么错误或指标。
2. **为什么出现。** 分开写已证实的直接原因、产生这个原因的设计或实现缺口，
   以及仍待验证的猜测。附文件、函数、报告、错误码或运行 ID。不能把推测写成事实。
3. **应该怎么修。** 在修改前说明方案、为何能解决原因、不能越过的边界、可能的
   副作用，以及怎样证明修改有效。不允许以“再试一次”替代原因分析。
4. **实际怎么修。** 列出真正修改的文件、函数、配置、数据版本和环境路径。
   解释相对原计划有什么变化、为什么变化；同时说明明确没有修改什么。
5. **怎么测、结果如何。** 保留执行目录、解释器、完整命令、退出码、测试数量、
   失败名称、错误信息、产物位置及版本。数值必须来自实际结果；未知项写未知。
   说明是模拟测试、真实官方资料检索、真实模型调用还是 GPU 执行。
6. **还剩什么、下一轮做什么。** 逐项写未通过、未测试、受阻内容，并对应下一轮
   的最小诊断动作和验证标准。只有实际通过的范围才能标为已解决。

问题来源要区分项目实现、配置或环境、外部服务、模型判断、评测设计和原因未明。
不能见到模型生成了错误补丁就断言是 API 故障，也不能见到外部超时就假定项目无错。

## 四、测试未达到要求时的处理

对当前任务验收中的失败继续下一轮，不在“运行结束”处停止。先分析失败，再做
有根据的修改，再测失败项及受影响路径。用户要求不重跑正确项，因此已成功且
不受修改影响的昂贵 GPU/API 单元不重复执行；扩大测试范围必须有明确理由。

“完美”不能解释成删掉失败测试、修改正确答案、放宽安全检查、泄漏隐藏数据，
或者无限抽样模型直到得到一次成功。先写清任务真正需要满足的验收条件；如果
条件后来需要调整，必须明确记录依据和用户决定，不能为了结果好看而事后更改。

比较方法、独立盲测和模型最终能力要与软件正确性分开。例如默认检索通过，不等于
其他备选检索方法也通过；应保留其失败，注明是否属于当前任务范围，不能全部报绿。
若某个剩余项不在已授权范围内，写出需要的决定，不擅自扩大任务、实验或费用。

遇到用户明确停止立即停止；遇到权限、缺失输入或外部条件阻塞，保留事实并说明
恢复条件，不承诺后台继续。重复失败两轮仍无新证据时，应换诊断方法，而非盲目重试。

## 五、证据、费用与保密

新测试尽量将原始输出和结构化结果保存到本地任务专用目录，文档记录路径和摘要。
原始材料含敏感内容时，不直接提交仓库；文档只保留必要的脱敏错误码和结论。
禁止写入密钥、完整环境变量、私有 holdout 内容或不应公开的模型输入输出。

记录代码提交、未提交变更状态、配置/知识库哈希及运行环境，避免拿另一份 checkout
的测试冒充当前版本。API/GPU 实验记录实际用量与可知费用；未知费用标为未知，
不当作零。不新增用户已明确拒绝的美元硬上限或余额检查。

文档变更本身不需要重跑 GPU、模型实验或全量代码测试；检查内容、链接和格式即可，
并明确本轮只更新记录。提交、推送及外部操作遵守当前授权，不因记录规则自动执行。
