# 历史回补 04：模型输出契约、补丁重试与 Planner 状态

回补日期：2026-09-29。证据包括 31a293c、52d319f、f81052a、cbddff5 的实际差异，
现有模式契约与定向复测文档，以及用户转述的外部分析。转述统计没有全部重新聚合，
以下明确标注，不能把外部云端通过数当成本机结果。

## 第一轮：只报 LLM_INVALID_OUTPUT，无法知道究竟哪里错

### 问题与原因

早期 E 的失败集中在 planner，外部分析提到 123 次 provider 调用全部属于 plan，
没有进入 diagnose/patch。失败输出长度较长只能形成预算对象回填的猜测，不能据此
确认某字段违规。运行预算与本地旧 schema 的上限可能不一致，也必须对实际执行提交
检查，而不能用另一 checkout 的源码解释当前结果。

### 应该和实际如何修复

应在本地 schema 校验阶段记录值无关的字段路径、错误类型、约束和输出 hash，
区分 JSON 解析、schema 和领域策略拒绝；不靠保存所有敏感原文诊断，也不直接删掉
任何未知字段让模型通过。f775c10/c7172c8 及后续 9d75699 的历史显示持续修订 schema、
终态调用记录与失败回放；9d75699 已纳入 provider output telemetry 测试。

本轮没有逐个复演早期 schema 拒绝，预算回填仍保留为当时假说而非最终根因。
后面的字段级错误码让新失败可直接定位，避免重复这种猜测。

## 第二轮：补丁内容失败，却被告知只修改 JSON 格式

### 问题和原因

针对 9d75699，外部分析称 C 有 7 个、D 有 9 个、E 有 1 个“已诊断但没候选”单元。
第一次多为 JSON 合法但 diff 内容被策略拒绝，重试却经常变成裸 diff。旧提示统一称
schema/scope validation 失败，要求 correct its format，没有解释外层 JSON 正确、
内部 diff 错误的区别。该提示具有误导性；但没有保存第一次原文的单元，不能进一步
断言一定是上下文、include 或末尾换行中的哪一项。

### 应该怎么修复

按真正失败阶段给原因码。JSON 正确时明确保留统一 JSON 外壳，并指明 diff 内容错误；
JSON 不合法时才解释转义和对象格式。日志保留受限原因码而非模型原文，不放宽补丁范围。

### 实际怎么修复与结果

31a293c 修改 provider.py、patching.py 和 prompts.py，加入允许列表原因码和各自修复
提示，例如 hunk_context_not_found、include_changed、fixed_input_length 等；提示保留
`{"unified_diff": ...}` 外壳，并要求上下文/删除行逐字匹配源文件。对应契约与遥测测试
同步更新。提交差异已核实，外部提及的 104 测试是其副本环境结果，不当作本机验收。

后续只选择剩余失败单元复测的方向合理，但此轮具体本机完整结果文件没有在本次补录
中逐项定位，不能只靠“剩六个”倒推出精确成功率。本篇把后续仍出现的问题继续保留。

## 第三轮：一次全 run 格式重试不足以覆盖不同调用阶段

### 问题与为什么出现

原 `_format_retried` 是单个布尔值，一次 planner 或 diagnose 格式重试就用掉后续
patch 的机会。另一些错误只有笼统格式失败，无法区分代码围栏、非法转义或截断。
这属于控制器契约与可观测性问题，不等于所有模型内容错误都该无限重试。

### 方案与实际修复

52d319f 把额度按 call kind 分开，各类别最多一次格式重试，仍计入总物理调用次数。
新增 JSON 形状分类与 JSON 专用重试说明；内容拒绝继续走其专门提示。改动明确更新
模式契约，不伪装成完全不改变行为的日志补丁。

外部补丁测试报告 233 passed、3 failed、8 errors，并称 holdout 相关基线也失败。
这是外部环境报告，本轮没有重建其环境验证“原本就失败”的归因。因此不写成该补丁
零回归已被证明。真实本地后续结果按后续版本各自记录。

## 第四轮：Planner 不知道还缺什么，重复动作或过早结束

### 问题和原因

E 既可能已有 finding 却缺文档而 finish，也可能反复 inspect 已读源码。删除固定
RuleRouter 流程后如果不暴露控制器状态，模型无法准确知道动作为何被拒。
这不是直接证明模型完全无能力，也不是证明只需提示词就能消除所有推理错误。

### 应该与实际怎么修复

52d319f 新增 PlannerState，提供已执行动作、已读范围、缺失的证据类别和上一拒绝原因。
`missing_evidence` 同时服务于状态反馈和 finish 检查，避免两套规则不同步。
仍保留一次重新规划边界，不给固定工具顺序和案例目标工具。诊断提示同时说明普通
运行成功不能否定带位置的 race/init/sync finding；补丁提示加入内存对象边界核对。

### 测试与后续

新增 agent_loop 与 telemetry 测试可检查状态来自控制器而非模型自报。后续 case_0015/E
能完成调查并产生候选，是具体行为改善记录；但候选仍可能修错，不能把“进入 patch”
当作“GPU 验证成功”。该例后续见第 05 篇。

## 第五轮：允许可审计的格式规范化，不改变补丁内容

### 问题、原因和计划

case_0006/C 的转述记录中先出现整段 JSON 被代码围栏包住，之后 hunk_line_invalid。
该错误码把缺末尾换行、空上下文行无前缀、No newline 标记和非法首字符混在一起，
无法指导排查。应细分并只允许无歧义的外壳规范化，不能自动猜改 diff 上下文。

### 实际修改

f81052a 将上述行问题拆码；仅当全文恰好是一对完整围栏且内部是一个 JSON 对象时
去除围栏；仅为 diff 添加缺失的最终换行。`normalizations` 留下操作记录，
`output_sha256` 仍是原始文本 hash。之后继续完整 schema、scope 和源码匹配校验。
改动包括通用同步 API 提示和官方知识扩充，因而复测不是纯粹单变量实验。

### 测试结果与边界

外部报告 137 项通过、Ruff/mypy 通过属于其环境；本轮不转写为本地计数。
本地 `docs/v2-release-status.md` 记录 f81052a 上 case_0006/C 原生验证通过，
case_0015/E 仍失败。该结果不能证明所有格式情况已消失，也不能把两个案例混成一次
“全量修好”。后续新格式问题是额外 `$schema` 字段，见下一轮。

## 第六轮：诊断返回 Schema 而不是符合 Schema 的实例

### 问题和原因

e80ce75 开发批次有两项终态输出契约拒绝，公开调用分析指出额外 `$schema` 字段
触发 extra_forbidden。模型错误与系统反馈不足是两层问题：不能擅自删除字段放行，
但重试应该说明要返回实例，而不是 JSON Schema 定义。

### 实际修复与检查

cbddff5 为 extra_forbidden 添加对应说明，并保留重复错误仍被拒绝的检查。
历史文档记录相关 71 项测试通过。随后仅重跑原两项，各一次：case_0012/B/repeat1
为模型声明无法判断、无补丁；case_0002/E/repeat2 为 VERIFIED_FIXED。
完成文件本次已核对绑定 cbddff5，两个单元执行完成。

两项此次首次输出就合规，没有触发新增重试。因此结论只能是“本次未再次发生该格式
失败”，不能证明正是新重试提示带来了成功。case_0012 无法判断也不能改写成修复成功。
该轮和超时六项的统一统计见第 06 篇。
